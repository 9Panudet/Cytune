# D4 — measurement rig died after the isolcpus reboot: hotplug-fragile thermal channels + governor-loop EBUSY

**Step:** 0.2.4 (pilot2). **Date:** 2026-06-12. **Status:** fixed, validated.
**Commits:** `aec6548` (thermal + sibling policy), `676d923` (governor loop; pilot2 raw).

## Summary

After the pre-registered `isolcpus=3,7` reboot, the measurement rig could not run:
`thermal_log.sh` crashed reading a hardcoded coretemp channel that no longer existed,
and re-runs of `scripts/host_prep.sh` died mid-script with EBUSY before ever reaching
the code meant to fix the sensor situation. Two independent bugs. Fixed by label-driven
thermal-channel discovery with NA fallback and a reordered, online-CPUs-only host_prep.
Validated by a clean pilot2 in which both reference kernels pass the §5.1 calibration
target. No measurement was ever taken unmonitored — the wrapper's fail-closed design
aborted the pilot attempt correctly.

## Symptom

```
cat: /sys/class/hwmon/hwmon1/temp5_input: No such file or directory   (pilot2 attempt 1)
scripts/host_prep.sh: line 17: echo: write error: Device or resource busy  (re-runs)
```
Plus the downstream observable: cpu7 stayed offline across host_prep re-runs
(kernel log: last hotplug event `smpboot: CPU 7 is now offline` at 10:16, no
subsequent online), and coretemp exposed only `Package id 0, Core 0..2` — no `Core 3`.

## Root cause

Two mechanisms, one trigger (cpu7 offline on the isolcpus boot):

1. **Hotplug-fragile thermal addressing.** `scripts/thermal_log.sh` read
   `$HW/temp5_input` by fixed index, assuming the boot-time enumeration
   (temp1=Package, temp2..5=Core 0..3). coretemp (de)registers per-core channels with
   CPU hotplug; after this boot's `host_prep.sh` offlined cpu7, the `Core 3` channel
   de-registered (and did NOT re-register when cpu7 was later onlined — on this boot
   the channel is gone until module reload or reboot). `temp5_input` vanished →
   `cat` failed → `set -e` killed `line()` → snapshots failed → `measure_wrap.sh`'s
   own `set -e` aborted the pilot before measuring (correct fail-closed behavior).
2. **Governor loop wrote to an offline CPU's policy.** `host_prep.sh` looped over the
   glob `cpu[0-9]*/cpufreq/scaling_governor`. Offline cpu7 retains a lingering
   `cpufreq -> ../cpufreq/policy7` symlink, so the glob matched it; writing an
   offline CPU's `scaling_governor` returns EBUSY → `set -e` killed the script at
   line 17 — BEFORE the isolcpus-aware sibling branch (added in `aec6548`) could
   online cpu7. Every "re-run host_prep" therefore looked like the fix didn't work.

## Why it produced the symptom

Bug 2 masked the fix for bug 1: the sibling-online branch that would have restored
sensor coverage sat *after* the governor loop, which died first on exactly the boots
where the fix mattered (cpu7 offline). The visible behavior — "ran host_prep, cpu7
still offline, Core 3 still missing" — pointed at the new branch, while the actual
fault was three lines earlier in untouched code.

## Fix

- `thermal_log.sh` (`aec6548`): channels resolved **by label** (`chan()` scans
  `temp*_label` for "Package id 0"/"Core N"); a missing channel yields `NA` in the
  CSV, never a crash. A `set -e` lifetime bug in the first version of `chan()`
  (falling off the loop returned status 1, killing the script inside command
  substitution) was caught in the same session and fixed (`return 0`).
- `host_prep.sh` (`676d923`): step order swapped — sibling policy FIRST (online cpu7
  when `isolcpus` covers 7; offline fallback otherwise), THEN the governor loop,
  which now iterates **online CPUs only** (cpu0's missing `online` file treated as
  online) and still hard-fails on a real governor-write error.
- `pilot_stats.py` thermal basis: `core3` when the channel exists, else `package`
  (die-level signal; recorded in `MEASUREMENT_CONSTANTS.json` as `thermal_basis`).
- This addresses the root causes (index-based addressing; offline-policy writes) —
  not the symptoms: no `|| true` was put on the governor writes for online CPUs, and
  thermal NA is visible in the data, not hidden.

## How it was found

Deterministic repro: every host_prep re-run on this boot. The kernel journal
disproved "the branch ran but didn't work" (no cpu7 online event existed at all
→ the script never got there). The decisive evidence was the human's pasted stderr:
`line 17: echo: write error: Device or resource busy` — line 17 is the governor loop,
upstream of the sibling branch. A manual `echo 1 | sudo tee .../cpu7/online`
confirmed onlining works fine (kernel accepted it), isolating the EBUSY to the
offline-policy write. Hypotheses rejected en route: stale-script execution (disproved
by mtime timeline once, then conclusively by the line-17 error), kernel refusing to
online isolated CPUs (disproved by the manual tee).

## Why it slipped through

Workload gap: both scripts were written and tested on boots where all 8 CPUs were
online at script start (0.2.1) — the glob never met a lingering offline policy, and
temp5 always existed. The isolcpus reboot plus the old script's own cpu7-offline
created the first boot state that violated both assumptions. The rig's fail-closed
design (measure_wrap aborts without thermal) worked as intended — the defect cost a
blocked pilot, never a bad measurement.

## Validation

- `thermal_log.sh snapshot` on the degraded boot: emits `...,NA,0,0,3600000,1,performance` — no crash.
- `measure_wrap.sh --verify-only`: PASS under both sibling states (offline earlier;
  online+isolated after the manual tee).
- **Pilot2 end-to-end clean** (the original failing workload): both kernels K=30 on
  the isolated core — csr_scale CI@30 = 0.315%, pava 0.345% (target ≤1%), cycles
  cross-check 3.5998/3.5996 GHz vs 3.6 (0.01% dev), throttle 0
  (`results/pilot/raw2/`, `results/pilot/PILOT2_REPORT.md`).
- Coverage statement: the host_prep online-CPUs-only loop is validated on this boot
  state (cpu7 initially offline, then online); the offline-fallback branch (boot
  without isolcpus) has not been re-executed since the rewrite — it will run at the
  next non-isolcpus boot, where the wrapper independently verifies the result.
