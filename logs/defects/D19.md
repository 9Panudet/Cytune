# D19 — the CF-1 busy predicate matched its own caller's command line and reported BUSY on an idle box

**Step:** P4-alpha resume pre-flight (Stage 1). **Date:** 2026-07-25.
**Status:** fixed, validated (2 new tests, one of which is a non-vacuity control; live check).
**Raw:** `scripts/hooks/campaign_busy.sh`, `scripts/hooks/test_graphify_gate.py`. Recompute:
`podman run --rm -v "$PWD/scripts":/w/scripts:Z -w /w --network=none localhost/motifbo-tools:phase1
python3 -m pytest scripts/hooks/test_graphify_gate.py -q`.

## Summary

`campaign_busy.sh` decides whether a campaign build/measure cycle is live, and everything else
(the graphify post-commit gate, the drain, my own status sweeps) trusts it. It used `pgrep -f`,
which matches whole command lines — including the command line of the shell that invoked the
predicate. Running it from a shell whose command contained the literal text `measure_wrap.sh` made
it report BUSY on a completely idle box. Fixed by excluding the caller's own process ancestry from
the match.

## Symptom

During the Stage-1 pre-flight, one compound command ran `measure_wrap.sh --verify-only` and then
the predicate. The predicate said:

```
a timed measurement (measure_wrap/measure_child) is in flight
(BUSY)
```

and the post-commit hook agreed:

```
[graphify hook] DEFERRED — a timed measurement (measure_wrap/measure_child) is in flight
```

`ps -eo pid,ppid,args | grep -E 'measure_wrap\.sh|measure_child\.py'` at the same moment:
**no real measurement process existed.** Re-running the predicate from a shell whose command line
did *not* contain the string returned IDLE.

## Root cause

```sh
if pgrep -f "[m]easure_wrap\.sh" >/dev/null 2>&1 || pgrep -f "[m]easure_child\.py" ...
```

`pgrep -f` matches against `/proc/<pid>/cmdline` for every process. The `[m]` bracket idiom is a
`grep`-era trick that stops the *matcher* from matching itself; it does nothing about **other**
processes whose command line legitimately contains the pattern — in particular the invoking shell,
whose `bash -c '...'` command line embeds the entire compound command the predicate is part of.

The same mechanism produced two earlier confusions in this session that I attributed to noise:
a status sweep reported `RUNNER ALIVE (unexpected)` for `run_fleet.py` when no runner existed,
because the sweep's own command line contained `run_fleet.py`.

## Why it produced the symptom

Both `campaign_busy.sh` call sites treat a non-empty `pgrep` result as "a measurement is running".
With the caller matched, the predicate became "does anyone, including me, mention this string?" —
which is true by construction whenever the predicate is invoked from a script that also mentions
the tools it guards. That is the common case: the pre-flight, the steward tick, and the drain all
name these tools.

## Fix

`scripts/hooks/campaign_busy.sh` now walks its own ancestry via `ps -o ppid=` and filters those
PIDs out of every match:

```sh
_SELF=" $(_ancestry | tr '\n' ' ') "
others_matching() {
    for pid in $(pgrep -f "$1" 2>/dev/null); do
        case "$_SELF" in *" $pid "*) continue ;; esac
        printf '%s\n' "$pid"
    done
}
```

All three checks now use `others_matching`. The in-flight-marker check (a file test) was never
affected.

## Direction of failure — why this was not a correctness event

It failed **SAFE**: the predicate over-reported busy, so the F1 gate deferred rebuilds that could
have run and the drain would have refused work it could have done. No measurement was contaminated
and no gate was bypassed. But a safety predicate that cannot distinguish "a measurement is running"
from "someone typed the tool's name" is not trustworthy in the other direction either, and it is
about to be the heartbeat signal for an unattended multi-hour campaign — so it is fixed now rather
than tolerated.

## How it was found

The Stage-1 pre-flight printed `(BUSY)` immediately after `measure_wrap --verify-only` returned
exit 0 with no runner alive. Those two facts are incompatible, which forced the check.

## Why it slipped through

**Test-environment gap.** `test_graphify_gate.py` invoked the predicate via
`subprocess.run(["bash", str(script)])`, whose command line is just the script path — it never
contains the guarded patterns. Every existing test therefore exercised the one calling convention
immune to the bug. The failure needs a caller whose command line mentions the tools, which is how
humans and steward scripts actually call it.

## Validation

- `test_predicate_ignores_its_own_callers_command_line` — invokes the predicate from a shell whose
  command line contains all three patterns; asserts IDLE.
- `test_predicate_still_detects_a_genuine_measurement` — **non-vacuity control**: spawns a real
  process named `measure_child.py` via `exec -a` and asserts BUSY. Without this, a predicate that
  simply never reported busy would pass the first test.
- Live: `bash -c '# measure_wrap.sh\nbash ./scripts/hooks/campaign_busy.sh'` → IDLE (correct).
- 8 passed, 1 skipped in `motifbo-tools:phase1`; the live-hook guard check passes on the host.
