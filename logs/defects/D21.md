## Summary

`P2_REPORT` §5d compares each Dataset-R anchor's v1 characterisation against its Phase-P
measurement, and flags a ratio ≥ 2× for investigation before the freeze (the R3/D5 discipline). It
compared **v1's `delta_all`** against **Phase P's committed `delta_all`**. Those are not the same
quantity. v1's is `t_worst / t_best` — the full landscape span. Phase P's is `t_ref / t_star` — the
speedup of the best config over the **reference/default** config. The ratio between them is
therefore `t_worst / t_ref`, a statement about how slow the worst config is relative to the default,
which carries no information about cross-version agreement at all.

On `elkan` that produced a **2.41× INVESTIGATE flag** — a fabricated finding that would have gone
into the checkpoint report as evidence of a measurement problem.

## Symptom

`elkan` landed as the 8th anchor:

```
elkan  LEVER-SEP  P D_str=1.6311  v1 end=3.9290  ratio 2.41  -> TRIPS the >=2x bar
```

`elkan` was also the single most plausible candidate for a real discrepancy: heaviest build, the
only cobuild-with-OpenMP anchor, never measured at any scale before this phase, 8.92 h cycle
(3.5× the anchor average), and the largest v1 Δ in the corpus. Every prior about it said "this is
where a real problem would show up."

## Root cause

```python
# scripts/phasep/classify.py:75
delta_all = t_ref / t_star          # t_ref = REFERENCE config; t_star = best feasible
```

versus v1's record, whose `delta_all` is built from `t_best_ns` / `t_worst_ns`:

```
t_best_ns: 53371719   t_worst_ns: 209696346   delta_all: 3.9289786787643095
```

`209696346 / 53371719 = 3.929`. v1 = span. Phase P = speedup-over-default.

For elkan the reference config sits at ≈65.9 ms (by construction — the R driver calibrates the
reference into the pre-registered 50–80 ms band) while the best config is 40.4 ms and the worst is
146.5 ms. So:

- P committed Δ_all = 65.9 / 40.4 = **1.63**
- P actual span = 146.5 / 40.4 = **3.89**
- the "transfer ratio" I computed = 3.93 / 1.63 = **2.41** = `t_worst / t_ref` ≈ 146.5 / 65.9 ✓

The flag was arithmetic on mismatched definitions, nothing more.

## The disproof that settled it

Rather than reason about scale or OpenMP, all 16 of v1's configs were matched **individually** into
Phase P's Θ and compared config-for-config:

| label | v1 ms | P ms | v1/P |
|---|---|---|---|
| UPHT | 53.37 | 40.39 | 1.32 |
| UCHT | 55.12 | 40.37 | 1.37 |
| … | … | … | … |
| SPLT | 209.37 | 146.32 | 1.43 |
| SCLT | 209.70 | 146.50 | 1.43 |

Phase P is uniformly **1.32–1.43× faster on every single config** — a near-constant offset,
consistent with the calibrated scale (n_samples 334,206 vs v1's 500,000). A uniform scale factor
cancels in a ratio, so:

- v1 span over those 16 configs: **3.9290×**
- P span over the **same** 16 configs: **3.6293×**
- P span over the full 1728: **3.8939×**

`elkan` transfers at **1.009×** — the *closest* agreement of all nine anchors, not the worst.

## Two hypotheses this killed on the way

1. **"P builds elkan serial, v1 built it parallel."** False, and I had asserted it in a prior
   commit. `build.py:119` does consume the flag —
   `omp = ["-fopenmp"] if meta.get("openmp") else []` — and both OpenMP anchors carry
   `openmp: true`. v1 passed `-fopenmp` too (`delta_probe_pkg.py:59`). The original claim came from
   grepping `build_phase.py`, `measure_phase.py`, `measure_child.py`, `measure_wrap.sh`, finding
   nothing, and concluding from four misses that nothing anywhere read the flag — without checking
   `build.py`. **Four negative greps are not a proof of absence.** What survives is narrower and is
   a driver property: `elkan_setup`/`predictor_setup` pass `n_threads=1`, as v1 did.
2. **"The 16-config screen and the 1728 Θ aren't comparable spaces."** False — all 16 matched
   exactly once the encoding was decoded (`T`→`fmffp=('off','off')`, `A`→`('on','NA')`,
   `L`→`-O1/x86-64/funroll omit`, `H`→`-O3/native/funroll on`).

## A self-inflicted detour worth recording

The first two config-matching runs reported **"NO MATCH" for all 16 configs**, which looked like
strong evidence that the two config spaces were disjoint. They were not. The Phase-P table nests
its timing under `row["screen"]["median_ns"]`, and the extractor read a non-existent top-level
`row["median_ns"]`, so the lookup dict was built **empty** and every probe missed by construction.

Both runs were entered in the ledger as evidence and then had to be **retracted** — they measured
my extractor, not the data. Mantra step 4 exists for exactly this: a breadcrumb that turns out to
be a bug in the instrument has to be struck from the ledger, not carried forward as a fact. Had I
accepted "NO MATCH ×16" at face value it would have become a second fabricated finding
("v1 and Phase P sweep incompatible config spaces") layered on top of the first.

## Fix

§5d now compares **span vs span**: v1's `delta_all` against Phase P's own worst/best span,
recomputed from the frozen table. Phase P's committed `delta_all` is still reported, in its own
column, labelled with its actual definition. The section carries an explicit METRIC IDENTITY
paragraph so the next reader cannot repeat the substitution.

P's span is consistently ≥ v1's (ratios ≤ 1) because P sweeps 1728 configs against v1's 16 and so
finds wider extremes — the expected direction, and a mild positive control on the comparison
itself.

## Lesson

D5 taught "do not compare against a contaminated number." D21 is its neighbour: **do not compare
two numbers that share a name.** Both v1 and Phase P call their quantity `delta_all`; they are
defined differently, and the identical key made the substitution invisible. The §5d table now
states the identity of every column in the report text rather than relying on the field name.

Generalised guard for the remaining P-2 work: any cross-version or cross-tool comparison must state
each side's **definition**, not just its label, before a ratio is taken. This applies directly to
the pending audit battery, where the stats-auditor recomputes quantities that exist under the same
names in three different artifacts (`class_v2.json`, the ledger, and the manifests).
