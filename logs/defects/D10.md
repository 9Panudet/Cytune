# D10 — P-2 report counted SLOT_EXHAUSTED ledger entries, not distinct slots (attrition inflated by relaunch count)

**Step:** P-2 synth stage, ~30/130. **Date:** 2026-07-20. **Status:** fixed, validated (revert-check
+ 71 tests green). **Raw:** `results/fleet/fleet_ledger.jsonl` — 25 `SLOT_EXHAUSTED` entries against
5 genuinely exhausted slots. Recompute:
`python3 -c "import json;r=[json.loads(l) for l in open('results/fleet/fleet_ledger.jsonl')];e=[d for d in r if d.get('status')=='SLOT_EXHAUSTED'];print(len(e), len({d['kernel_id'] for d in e}))"`
→ `25 5`.

## Summary

`report_p2.build_report` counted attrition with a flat filter
(`[e for e in led if e.get("status") == "SLOT_EXHAUSTED"]`) over an append-only ledger in which an
already-exhausted slot is **re-ledgered on every relaunch**. The rendered figure
("exhausted slots: N", report line 86) therefore scaled with the number of times the campaign was
restarted rather than with the data: 5 real exhaustions read as 25 after five relaunches.

This feeds CHECKPOINT P-2 §1 (per-regime counts / attrition vs the n=26 power floor) and §3
(diversity evidence). Left unfixed it would have overstated attrition ~5× in a decision-grade
report — the precise failure mode the roadmap's "count before 'all'" rule exists to prevent.

## Root cause

Two correct behaviours composed into a wrong statistic:
1. `run_fleet.process_slot` has no "already terminal" guard, so a relaunch re-walks an exhausted
   slot. This is *cheap and harmless* — every re-attempt hits the `PARAMS_DUPLICATE` pre-guard (D8),
   so no build or measurement is burned — and it keeps the ledger a faithful append-only record of
   what the runner actually did.
2. The report treated one ledger *entry* as one *slot*. `SLOT_EXHAUSTED` is terminal per slot, so
   entries beyond the first are relaunch artifacts, not data.

Session-limit kills made the campaign restart far more often than the design anticipated (5×),
which is what made a latent counting bug numerically loud.

## Fix

`report_p2.py`: dedupe `SLOT_EXHAUSTED` by slot identity (`kernel_id`/`slot`) before counting.
`REJECTED_CLONE` is deliberately **left undeduped** — one slot may legitimately accrue several
distinct clone-rejections (different parameterizations) before it accepts, and each is a real
measured attempt. Raw ledger and runner are untouched: the fix is to the *derived statistic*, not
the record.

## Validation

New `scripts/phasep/test_report_p2.py` (3 tests): dedup correctness, the non-vacuity guard, and
empty-ledger snapshot robustness. **Failure path verified** — reverting only the dedup line in a
throwaway copy fails 2 of 3 tests; the fixed form passes. Full suite **71 passed** in X′.

## Lesson

Ledger entries are events, not entities. Any statistic derived from an append-only log under a
resumable runner must state its unit of count (`per event` vs `per slot`) and dedupe accordingly —
otherwise the number silently encodes operator history (how often we restarted) instead of
measurement. Every remaining ledger-derived figure in `report_p2` was audited for the same class:
`ACCEPTED` (30 entries / 30 distinct) and `REJECTED_CLONE` (5 / 5) are 1:1 and correct as written.
Caught by a heartbeat tick **before** the checkpoint report was ever generated.
