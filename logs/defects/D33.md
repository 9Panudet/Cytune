# D33 — a test that read the host's image store instead of the code it named

**Step:** launch closeout, item 4 (claim/evidence reconciliation). **Date:** 2026-08-13.
**Status:** fixed, validated (six interpreters green after the fix; all six red before it).
**Found by:** running the D3 stability-matrix cell the launch pass had left **NOT RUN** — the host
interpreter range. Not by a reviewer, not by a tester: by executing an untested claim.
**Raw:** `src/cytune/test_cytune_doctor.py:28`, `src/cytune/doctor.py::_check_sanitizer_gate`,
`src/cytune/sanitize_gate.py::is_pinned_image`.
Recompute: `scripts/release/pymatrix.sh` · logs in `results/release/pymatrix/`.

## Summary

`pyproject.toml` claims `requires-python = ">=3.9"`. Every run in the launch pass used one
interpreter, 3.14.5. Five of the six supported versions had never executed a line of this code, so
the claim covered five versions no measurement had touched — which is what item 4 of the closeout
directive was about, and the reason to run them rather than narrow the claim.

All six came back with the same single failure:

```
FAILED src/cytune/test_cytune_doctor.py::test_failure_path_sanitizer_check_passes_when_the_image_is_present
1 failed, 750 passed, 20 skipped
```

Identical on 3.9, 3.10, 3.11, 3.12, 3.13 and 3.14 — which is itself the diagnosis. **Nothing about
it is a Python-version property.** What the matrix actually surfaced is that the test was never
about the code.

## Root cause

```python
def test_failure_path_sanitizer_check_passes_when_the_image_is_present(monkeypatch):
    """Non-vacuity: the check discriminates on the image, rather than always failing."""
    monkeypatch.setattr(doc, "_run", lambda cmd, timeout=30: (0, "", ""))
    tier, ok, _d, fix = doc._check_sanitizer_gate()
    assert ok is True and fix == ""
```

`_check_sanitizer_gate` has **two** external dependencies, not one:

```python
unpinned = not sanitize_gate.is_pinned_image()      # shells out to podman ON ITS OWN
rc, _o, _e = _run(["podman", "image", "exists", IMAGE])   # the one the test stubbed
```

`is_pinned_image()` resolves the image digest through `rig`, never through `doctor._run`, so the
monkeypatch does not reach it. The assertion therefore reads **the host's image store**: it passes
on a machine where the pinned image is present and fails everywhere else.

The docstring is the tell. It claims non-vacuity — "the check discriminates on the image, rather
than always failing" — and the discrimination it observed was real podman answering a real
question, with the stub contributing nothing to the outcome. A test that passes for a reason other
than the one it states is the R2/D-3 class, and here it was inside a test *written to prevent* that
class.

## Consequences, which are worse than one red test

1. **`pytest -q src/cytune` does not pass on a clean machine.** `docs/CONTRIBUTING.md` gives that
   command as the product suite and says it must pass with no `scripts/` and no `results/`. It
   silently also required the pinned toolchain image — a several-minute container build — so the
   first thing a new contributor sees is a red suite with a failure that has nothing to do with
   anything they did.
2. **The H6 branch had no test at the doctor layer at all.** The `unpinned` path — podman has an
   image under the pinned name and its digest is somebody else's, i.e. `podman tag stub
   localhost/motifbo-env:phase1` — reaches the one check whose job is to warn a user before they
   spend an hour measuring, and nothing exercised it. The broken stub had been standing in front of
   it, always taking the other branch.

## Fix

`src/cytune/test_cytune_doctor.py` — stub both dependencies, so the test is about the function
again:

```python
monkeypatch.setattr(doc, "_run", lambda cmd, timeout=30: (0, "", ""))
monkeypatch.setattr(sanitize_gate, "is_pinned_image", lambda: True)
```

…plus `test_an_image_that_exists_but_is_not_the_pinned_one_is_not_a_pass`, which drives the branch
consequence (2) named: `DEGRADED`, `ok=False`, `NOT the pinned toolchain` in the detail and
`--apply refuses` in the fix text.

against the same tree, was red on all six before it and green on all six after.

## The class

**An untested claim is not a small debt; it is an unopened box.** `requires-python = ">=3.9"` had
been in `pyproject.toml` since packaging. Nobody doubted it, there was no reason to, and the cost of
finding out was one script and eleven minutes. What came out was not a Python incompatibility — the
product genuinely does not care which of these interpreters it runs on — but a test that had been
reading the developer's machine for its entire life.

That is the second time in two passes that **running something nobody had run** produced a finding
no amount of reading produced: D25 was a script dead on import for a whole release, and this is a
test green for the wrong reason. Both were invisible for the same reason — *absence of a signal
reads as success* — and the fix in both cases is to execute the thing, not to inspect it harder.

It also belongs to the sibling class the closeout swept for: `docs/GUARANTEES.md`'s control table
asks of each guarantee whether a deliberately wrong input makes it fire. This test asked that
question of itself in its docstring, answered yes, and was wrong — because a stub that does not
cover every path into the function under test leaves the real world supplying the answer.
