# D3 — `import smac` ImportError: private sklearn symbol removed, smac uncapped

**Step:** 0.1.3 (Python/Cython/SMAC3 pinning). **Date:** 2026-06-11. **Status:** fixed, validated.
**Numbering note:** D1/D2 are reserved for the prior-project defect history (roadmap §0.2);
new defect records in this repo start at D3.

## Summary

The freshly resolved hash-pinned Python environment was unusable: `import smac` raised
`ImportError` because pip-compile selected scikit-learn 1.9.0, which removed the private
symbol `sklearn.tree._tree.DTYPE` that smac 2.4.0 imports unconditionally at module load.
Fixed by adding a `scikit-learn<1.9` cap to `data/env/requirements.in` and re-resolving
(lock now pins scikit-learn 1.8.0). No tracking system yet (pre-git step); pointers are
this file, `logs/env/STEP_0.1.3_python_pins.log`, and the requirements.in comment.

## Symptom

In image `f9328a8a92f8`'s predecessor (lock with scikit-learn 1.9.0):

```
$ python -c "import smac"
  File ".../smac/model/random_forest/random_forest.py", line 14, in <module>
    from sklearn.tree._tree import DTYPE
ImportError: cannot import name 'DTYPE' from 'sklearn.tree._tree'
```

Deterministic — every import, no flakiness.

## Root cause

Three facts compose:
1. `smac==2.4.0`, `smac/model/random_forest/random_forest.py:14` does
   `from sklearn.tree._tree import DTYPE` at module top level; the import chain
   `smac/__init__ → callback → main.smbo → acquisition → model.random_forest` executes it
   on any `import smac`.
2. scikit-learn 1.9.0 removed `DTYPE` from the compiled `sklearn.tree._tree` extension
   (probe: `dir(_tree)` shows `NODE_DTYPE`, `Tree`, `TreeBuilder`… but no `DTYPE`).
3. smac 2.4.0's metadata declares `Requires-Dist: scikit-learn>=1.6.1` — **no upper
   bound** — so `pip-compile --generate-hashes` legally resolved the broken pair
   (smac 2.4.0 + scikit-learn 1.9.0).

## Why it produced the symptom

The lock was internally consistent and hash-verified — pip `--require-hashes` checks
integrity, not importability. Nothing in resolution or install can detect that one
package imports a *private* symbol another package deleted. First execution of
`import smac` is the earliest possible failure point, and that is exactly where it failed.

## Fix

`data/env/requirements.in`: added `scikit-learn<1.9` with a carried-caveat comment
pointing here. Re-resolved in-image with pip-tools 7.5.3 → lock moved scikit-learn
1.9.0 → 1.8.0 (only change to the resolution); rebuilt image → `f9328a8a92f8`.
This addresses the root cause (the resolver can no longer select the symbol-removing
version) rather than hiding the symptom (no vendoring, no sitecustomize shim).
Cap is revisited only if a smac release >2.4.0 drops the private-symbol import.

## How it was found

Per debug-mantra. Repro: bare `python -c "import smac"` in the built image (instant,
deterministic). Fail path: traceback names file+line; `grep` of the module confirmed the
import is unconditional and the only knobs are the two package versions. Hypotheses:
H2 corrupted wheel — rejected (hash-verified install; `_tree` imports coherently);
H3 numpy-ABI break — rejected (`_tree` loads, exposes a full API minus one symbol);
H4 path shadowing — rejected (traceback shows the single venv site-packages);
H1 version skew — confirmed by the designated disproof: smac's `Requires-Dist` shows
`scikit-learn>=1.6.1` uncapped, and `dir(sklearn.tree._tree)` lacks `DTYPE`.
Cross-reference: pyrfr absent from the lock + pyrfr listed only as an extra in smac's
metadata + `random_forest.py` importing only sklearn machinery — all consistent with H1
and with the sklearn-backend recording this step required anyway.

## Why it slipped through

Workload gap upstream, not a process gap here: smac 2.4.0 predates scikit-learn 1.9.0
and its uncapped dependency allows futures it was never tested against. Our own process
caught it at the first possible moment — the Step-0.1.3 probe runs `import smac` before
the lock is accepted — so the defect never reached a committed artifact.

## Validation

In the rebuilt image `f9328a8a92f8` (lock: scikit-learn 1.8.0):
- `python -c "import smac"` — passes.
- Full probe `scripts/probe_smac_backend.py` — passes: versions as pinned
  (Python 3.12.3, Cython 3.2.5, smac 2.4.0, scikit-learn 1.8.0, numpy 2.4.6),
  facade default model instantiates, `model.train(X, y)` + `predict` smoke runs,
  fitted forest MRO = `EPMRandomForest → sklearn.ensemble._forest.ForestRegressor`,
  BACKEND VERDICT: sklearn. Output recorded in `data/env/SMAC_RF_BACKEND.md`.
Coverage statement: validated for the import path and the default HPO-facade RF
surrogate train/predict path only; the full BO loop is exercised (TDD) at Step 1.4.2.
