# D24 — one of three demotion paths left the candidate's sanitizer verdict on a certificate emitting the reference

**Step:** DOE-v2 Stage 5, live nine-anchor confirmation. **Date:** 2026-08-10.
**Status:** fixed, validated (repro proven to fail without the fix; live re-run exits 0).
**Found by:** the live dogfood — `fleet_R_08_elkan` exited **1** under 674 green tests.
**Raw:** `results/release/dogfood3/runs/fleet_R_08_elkan.prefix.log` (the failing run),
`src/cytune/cli.py` verify stage, `src/cytune/test_cytune_binding.py::test_i4_3_*`.
Recompute: `.venv/bin/python -m pytest src/cytune/test_cytune_binding.py -k "demotion_path or forgets_to_reset"`.

## Summary

```
cytune: REFUSING TO CERTIFY — a claim could not be tied to the artifact behind it.
  violated invariant I4.3: the sanitizer gate reports config 966 but the emitted config is 288.
```

`cli.tune` gates the search's best **candidate** before deciding what to emit — deliberately, and
for a good reason recorded in the code: the §1.4 gate is a bug finder, not only an emission filter,
and gating only the eventual emission once let a real out-of-bounds read go unreported because the
offending config was dropped for being slow.

It stores that verdict in `san_emitted` — the variable meaning *"the gate on the config being
emitted"*. Three paths can then demote the candidate to the reference:

| path | what happens to `san_emitted` | correct? |
|---|---|---|
| sanitizer reports | never assigned (the assignment is in the `else` branch) | yes |
| emit margin missed | explicitly set to `None`, so the reference is re-gated | yes |
| **C1 wall clock not corroborated** | **left alone — still describing the candidate** | **no** |

On the third path the reference (288) was emitted while `san_emitted` still described config 966.
The re-gate at the bottom of the stage is guarded by `if san_emitted is None:`, so it was skipped,
and I4.3 refused the whole document.

**The refusal was correct.** The binding layer did exactly what 1.0.0 built it for: it declined to
emit a certificate about a run that did not happen. The defect is that the run reached that state
at all, where it should have produced an honest `no-safe-improvement` certificate emitting the
reference with no speedup claimed.

## Root cause

One variable serving two meanings across a branch. `san_emitted` is assigned the **candidate's**
verdict and is only re-interpreted as the **emission's** verdict by whatever runs afterwards. Two
of the three demotion paths remembered to invalidate it; the third did not. The C1 path was added
last (1.0.0, closing the under-claim half of H1) and did not inherit the reset its sibling twenty
lines below already performed.

## Why 674 tests did not catch it

Two independent gaps, and the second is the more interesting one.

1. **`corroborate_ratio` is tested exhaustively as a pure function** — four tests over its verdicts,
   including a power-curve sweep. None of them drives the CLI's *composition* of that verdict.
2. **The composition sweep existed and omitted this path.**
   `test_cytune_coherence.py::_as_the_cli_would` states its purpose as reproducing "the CLI's
   decision order, so the sweep exercises the real composition". It modelled the sanitizer and
   emit-margin demotions and not C1's. Worse, its endpoint fixtures carried **no `wall_ns`**, so
   `corroborate_ratio` returned `corroborated: None` for every row of the sweep — the branch was
   unreachable **in principle**, not merely unwritten.

A gate tested in isolation, and a composition that never composed it.

## Fix

`src/cytune/cli.py`, C1 rejection path:

```python
    "sanitizer": san_emitted,     # keep the candidate's CLEAN verdict where a reader sees it
}
winner = ref_id
san_emitted = None                # that gate described the CANDIDATE, not the emission
```

The candidate's verdict is preserved inside the `rejection` record rather than dropped: the config
was ASan-clean, only its *timing* was unaccountable, and that is a real result about the user's
code.

`test_cytune_coherence.py`: `_as_the_cli_would` now models all three demotion paths, `_endpoint`
builds records whose parent wall clock is consistent with their medians (so C1 can actually reach
both verdicts), and `test_the_c1_branch_of_the_composition_actually_executes` asserts the fixture
reaches `True` **and** `False` — an anti-vacuity check, because adding a branch to a mirror proves
nothing if the fixtures cannot enter it.

## Sibling found while validating this one — D-4

Auditing the C1 record exposed a second defect in the same family: `build_certificate` accepted
`screen_overheads` and did **not** forward them to `corroborate_ratio`, so the CLI gated on one
budget (the larger of half the claimed gain and 3σ of the run's own measured overhead spread) while
the certificate recomputed with a smaller one and reported *"measured over 0 screened configs"*
when the run had measured 33–49.

Measured effect on all nine anchors: **none** — half the claimed gain dominated 3σ every time, so
no budget and no verdict changed. It is therefore a **reporting** defect with a **latent**
correctness risk, and is recorded as that rather than as a realised one.
`test_d4_the_certificate_records_the_same_corroboration_the_gate_decided_on` constructs the window
where the two disagree (`0.5·gain < residual ≤ 3σ < (1+warmup/K)·gain`) and fails without the fix.

## The class, and whether it is closed

D-3 and D-4 are both **"the document and the decision were computed from different inputs"** —
the same class 1.0.0 shipped `binding.py` to close, one level up from the artifact hashes.

I4.3 caught D-3 in production, which is the class defence working as designed. Neither was caught
by tests, and the reason is the same both times: the *unit* was tested and the *composition* was
not. The countermeasure added here is narrow — the composition mirror now covers all three paths
and carries an anti-vacuity test. A general countermeasure (asserting that every value reaching the
certificate was computed from the same inputs the gate used) does not exist and is not claimed.
