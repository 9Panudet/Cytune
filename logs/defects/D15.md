# D15 — the emit threshold was a fixed 1.02, below the phantom-speedup floor produced by selecting the minimum over B configs

**Step:** P4-alpha CLI v0 (Amendment A-4), `bo-math-reviewer` live-engine audit, finding F6.
**Date:** 2026-07-25. **Status:** fixed, validated (commits `7bc35b9` then generalised; 8 tests).
**Raw:** reviewer's computation `results/audit/P4alpha/e3_cli_gate/scripts/cli_audit_checks2.py`
(section E). Recompute: run that script in `motifbo-env:phase1`.

## Summary

`cytune` certified an "improvement" whenever the endpoint speedup exceeded a hard-coded 1.02.
Tuning selects the **minimum** over B measured configs, which on a flat landscape is biased low by
selection alone — producing apparent gains of 1.064× (B=32, s=0.03) and 1.109× (B=32, s=0.05), both
above the threshold. The product could therefore certify pure measurement noise as a speedup, which
is the exact failure it exists to refuse. Fixed by replacing the fixed floor with a margin that
scales with the run's own measured endpoint spread: `max(2 × combined endpoint CV, τ)`.

## Symptom

No live failure. Found analytically before it could produce one. The reviewer computed
`E[max_B Z]` over 200,000 simulations (seed 20260725): 1.4207 (B=8), 1.7667 (16), 2.0719 (32),
2.3415 (64). For per-config log-noise `s`, a truly flat landscape yields an expected phantom
speedup of `exp(s·E[max_B Z])`:

| B | s = 0.03 | s = 0.05 |
|---|---|---|
| 8  | 1.044× | 1.074× |
| 32 | 1.064× | 1.109× |

The v0 threshold was 1.02. Every cell in that table clears it.

## Root cause

`src/cytune/certify.py::build_certificate` decided the verdict with:

```python
if is_reference or speedup is None or speedup <= 1.02:
    verdict = "honest-flat"
```

The constant encoded "this rig's ~2% noise floor" — a statement about the noise of a **single
measurement**. The quantity that actually needs bounding is the noise of a **minimum over B
measurements**, which grows with B and with the per-config noise. The threshold was dimensionally
right and quantitatively unrelated to the risk.

Portable rig mode makes it worse: it is the mode with no host quiescing, hence larger `s`, and it
is also the mode a user without root is most likely to run.

## Why it produced the symptom

The endpoint tier already removes most of the bias — the winner is re-timed fresh at K=30 and,
crucially, is **not re-selected**, so a phantom regresses toward the reference. What remained was
the residual: a config selected for being lucky at screen retains some of that luck at endpoint,
and a fixed 1.02 bar cannot tell that residual from a real 3% lever.

## Fix

`src/cytune/certify.py::emit_margin`:

```
margin = max(2 × sqrt(cv_winner² + cv_reference²), TAU)      TAU = 0.02
improvement  ⟺  (speedup − 1) > margin
```

`cv` is each config's coefficient of variation over its endpoint sub-measures. Deliberate choices,
recorded because they are v0's and not inherited:

- **CV, not SEM.** With 3–5 sub-measures, `cv/√n` would understate the spread; the honest direction
  for a tool that certifies speedups is the wider bar.
- **τ = 0.02 is inherited** (PREREG §1.1), not invented here. Only the 2× multiplier and the CV
  choice are v0's, and the certificate says so: *"v0 product rule, not a pre-registered study
  threshold."*
- The bar now **scales with what this particular run could actually resolve**, so a noisy portable
  run must clear a wider bar than a clean quiesced one.

An earlier, narrower fix added an endpoint-separation requirement (every winner sub-measure faster
than every reference sub-measure). That is retained as a cheap rank-based second guard and a
reported diagnostic, but it is **subsumed in practice** — both rules key off the same spread, and
for n ≥ 3 a winner whose top sub-measure reaches the reference's bottom necessarily has a CV wide
enough for the margin to catch it first. Recorded rather than presented as two independent guards.

## How it was found

`bo-math-reviewer`, invoked for the narrow question "may BO ship as a v0 tuning engine", flagged it
as F6 — explicitly outside its mandate and reported anyway because it is engine-independent. It
falls out of the same analysis needed for BO's incumbent: any select-then-claim procedure has this
bias.

## Why it slipped through

**Latent-by-construction.** The threshold was written while building the honest-flat path, before
any run existed to test it against, and the number was chosen by analogy to the rig's single-measure
noise floor. No test could have caught it: a fixed threshold behaves exactly as specified, and the
specification was the defect.

## Validation

- `test_emit_margin_scales_with_measured_endpoint_spread` — clean endpoints sit at τ, noisy
  endpoints widen the bar.
- `test_borderline_gain_inside_a_noisy_margin_is_refused` — a 1.099× gain on noisy sub-measures is
  refused, and the fixture asserts it clears the *old* 1.02 floor, so the test is non-vacuous.
- `test_same_gain_on_clean_measurements_is_accepted` — the same gain measured cleanly still
  certifies, so the fix does not simply suppress all improvements.
- `test_emit_margin_falls_back_to_the_floor_and_says_so_without_enough_subs`.
- Live: all three improvement verdicts in the smoke set still certify (their margins land at τ,
  CVs ≈ 0.001–0.01), and `pilot_C_01` remains honest-flat.
- Full suite: 82 passed, 1 skipped, in `motifbo-env:phase1`.

Not validated against a real high-noise run — no smoke run was executed under host load. The
portable-under-load case remains untested and is listed as a limitation in `CLI_V0_REPORT.md` §7.

## Action items

- The margin is stated in every certificate with its basis and its "product rule, not pre-registered
  threshold" caveat. Done.
- If v0 ever grows a `--budget` flag large enough for B ≫ 32, revisit: the bias grows with B while
  the margin does not know B. Open, not reachable at current budgets (16–40).
