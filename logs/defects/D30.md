# D30 — a 215× calibration miss was reported as success, with a confident IMPROVEMENT verdict

**Step:** launch pass, section D3 (systematic-breaker agent). **Date:** 2026-08-12.
**Status:** fixed, validated live. **Raw:** `src/cytune/cli.py`, after the probe measurement.

## Summary

On a kernel whose single call is ~16 ns, the run printed

```
calibrated REPS: 1 -> 1431 (reference ~5.0 ms)
```

and the **same document** then reported `reference 0.023 ms` — a 215× miss — under
`VERDICT: IMPROVEMENT / 1.1709x`, with the standard separation and emit-margin language and a
directive header to paste into the user's source.

Grep over the full run output for `too small|below|resolution|microsecond` returned nothing.

## Root cause

`campaign.calibrate` extrapolates linearly from **one** measurement at the driver's current knob.
When a single call is dominated by constant per-call overhead, that extrapolation is badly wrong.
That limitation was already known and already documented in the code.

What was missing is that **nothing compared the requested target against the workload calibration
actually produced**, even though both numbers were in hand by the end of the probe stage.
`--target-ms` exists so the reference lands in the band where the v1.4 rig's timing guarantees were
established; at 23 µs the run is far outside anything the study validated.

## Fix

After the probe measures the reference, cytune compares achieved against requested:

* **below 1 ms → REFUSE**, exit 1. This is the same rule already applied to `--target-ms` itself
  ("below this rig's timing resolution"), arriving by a different route; it was enforced on the
  argument and not on the result.
* **more than 3× off in either direction → warn loudly**, and say that every number below describes
  the workload actually measured.

Reported rather than corrected in the second case: re-calibrating in a loop spends the search's
budget on calibration, which is a standing decision already recorded in the code.

## Validation

Live, on the breaker's kernel:

```
calibrated REPS: 1 -> 2167 (reference ~5.0 ms)
cytune: REFUSING TO TUNE — the calibrated workload is 0.0400 ms, below this rig's
  timing resolution. You asked for ~5 ms and calibration missed by 125x.
```

exit 1, where the previous behaviour was `IMPROVEMENT 1.1709x`, exit 0.

## Class

**"The tool had both numbers and never compared them."** The same shape as D26 (the oracle's golden
was in hand and nothing asked whether it could discriminate) and D24/D-4 (the document and the
decision computed from different inputs). All three are cases where the evidence needed to refuse
was already present.
