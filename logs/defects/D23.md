## Summary

Roadmap §1.4 makes ASan+UBSan a **feasibility gate**: a candidate that reports is infeasible,
independently of whether its output is correct. **The Phase-P fleet harness never invoked it.**
Every one of ~149 kernels × 1,728 configs was gated on the oracle alone — an output comparison
against a golden. An output check cannot see a read that happened to produce the right answer.

The bounded remediation found that it missed some. Of 34,128 (kernel, config) cells that execute a
planted out-of-bounds read, **1,296 are recorded FEASIBLE** in the frozen tables. All 1,296 sit in
**3 kernels**, where they are 432/432 — i.e. in those three the oracle caught *none* of it, while
in the other 76 armed kernels it caught *all* of it.

For those three, the entire measured lever was the out-of-bounds read:

| kernel | class | Δ_all | Δ_strict | infeas frac |
|---|---|---|---|---|
| `fleet_INT_14_int_min32` | INT → **MID** | 13.14 → **1.32** | 12.42 → **1.32** | 0.25 → 0.50 |
| `fleet_INT_16_int_max32` | INT → **MID** | 13.01 → **1.32** | 13.01 → **1.32** | 0.25 → 0.50 |
| `fleet_INT_20_int_sum64_r3` | INT → **MID** | 13.92 → **1.32** | 13.92 → **1.32** | 0.25 → 0.50 |

A 13× speedup that is really 1.32×. The other ~11.8× was the cost of the bounds check on a kernel
that, without it, read memory it did not own.

## Mechanism

The `trap_wrap` feasibility variant is a DESIGNED trap — it is what makes the
boundscheck/wraparound pair a correctness lever rather than a pure speed lever. The driver passes
`guard=1`; the kernel computes `j = i - off` with `off=1` and reads `a[-1]`:

```cython
if guard is not None:
    off = <Py_ssize_t>guard      # trap variants pass off=1: i-off = -1 on the first lap
...
    j = i - off
    acc = a[j] if a[j] < acc else acc
```

On a typed memoryview, `wraparound=False` means `-1` is **not** translated to `n-1`; it is used as
written. So the UB-executing set is exactly

```
{config : boundscheck=False ∧ wraparound=False}   = 432 of 1,728
```

— with `boundscheck=True` Cython raises `IndexError` before the read, and with `wraparound=True`
the index wraps in-bounds and is well defined. This is derived from `theta`, not enumerated by
hand, and it reproduces exactly.

**Why the oracle caught 76 kernels and missed 3.** The three are min/max reductions over random
`int32`. Executing the trap reads one garbage value from before the buffer and drops `a[n-1]`. For
a min/max reduction that changes the answer only if the garbage is more extreme than the true
extremum, or the dropped element *was* the extremum — over 16k–49k samples spanning ±2³⁰, neither
happens. The output matched the golden bit-for-bit and the oracle said `feasible=1, reason="ok"`.
Every other template accumulates or transforms elementwise, so one wrong element propagates into
the output and the oracle sees it (`oracle_mismatch`) or the read segfaults (`crash`).

The reduction's own robustness is what hid the defect. That generalises: **an output oracle is
weakest exactly where the computation is most forgiving**, which is not where one intuitively
looks for missed errors.

## Root cause of the LAPSE (the more important half)

The missed configs are a consequence; the cause is that a hard gate was documented and never
wired. `scripts/phasep/build.py` builds with `profiles.performance_argv` only. Nothing in
`build_phase.py`, `measure_phase.py` or `measure_child.py` ever calls `sanitizer_argv`. The
sanitizer machinery *exists* and is *correct* — `run_known_good_sanitize.py` used it at Step 0.4.2
and it works — it was simply never invoked by the Phase-P harness.

Nothing detected this for the entire campaign because **no artifact recorded the gate's absence**.
The per-config record has a `feasible` bit and a `reason`; there is no field that says *which
gates produced this verdict*, so a verdict from one gate is indistinguishable from a verdict from
two. A missing check leaves no trace unless something counts the checks.

## Remediation (and why it is an overlay, not an edit)

`FREEZE_MANIFEST.json` is write-once and carries a sha256 per `table.jsonl`. The measurements in
those rows are not in question — the timings are what the rig measured. What is wrong is the
**feasibility label**. So the raw stays byte-identical and the correction is recorded on top:

- `results/fleet/SANITIZER_INFEASIBLE_OVERLAY.json` — the 1,296 (kernel, config) cells forced to
  infeasible, derived mechanically from `spec.json` + `driver.py` + `theta`, with the rule and the
  evidence pointer. Regenerating it is deterministic.
- `results/fleet/<kernel>/class_v2_san.json` — the re-classification with the overlay applied.
  `a2_reclassify.reclassify(kdir, overlay=…)` recomputes Δ_all as well as Δ_strict, because the
  committed Δ_all's argmin was itself an overlaid config: quoting it would credit the kernel with
  a speedup the product is forbidden to emit.
- `run_fleet._cell_of` consults the corrected map. The append-only ledger still carries the
  uncorrected `measured_v2`, deliberately — history is evidence — so the correction is applied at
  the single point where the cell rule lives, and every consumer (report, power, study, routing)
  inherits it.

**Effect on the checkpoint.** INT 41→38 as-measured, 30→29 on the §4-conformant set; MID 26→29 and
24→25. No floor verdict flips: still **1 of 4** confirmatory cells at or above n=26 (INT).

## Scope of the audit, stated so it cannot be overread

114 units = 38 kernels (29 template representatives + 9 Dataset-R anchors) × 3 corners, at
`{reference}`, `{checks-off, -O3, native, funroll}`, `{checks-off + fast-math, native}` — three
distinct `theta.safety_class` keys. **This is not the §1.4 gate.** It does not cover the other
1,725 configs per kernel, nor parameterization differences within a template family. It is
evidence about the corners where UB is most likely, and it must be cited that way.

## A coverage gap I caused and had to fix mid-run

The first full run reported all 27 Dataset-R units as `RUN_FAIL_NO_TOKEN` — the R drivers
`import corpus_drivers`, which sits in the sibling `scripts/corpus` package that `san_child.py` did
not put on `sys.path`. Those 27 were **unaudited, not clean**, and the harness reports the two
under different names for exactly this reason: an un-run check must never tally as a passed one.
Fixed by mirroring `measure_phase.py`'s path setup; the R anchors then audited clean.

## Falsification trail

The first hypothesis was that every sanitizer report was a planted trap already caught by the
oracle — i.e. zero new findings. The disproof was cheap and decisive: for every armed trap kernel,
look up the corner's `config_id` in the frozen table and check its recorded `feasible` bit. Three
kernels came back `1 ("ok")`, which killed the hypothesis. Building and running those three under
ASan then confirmed heap-buffer-overflow on each. Had the disproof not been run first, "all
reports are known traps" was a comfortable and completely wrong conclusion that fit every
observation up to that point.

## Lessons

1. **A gate that is documented but not wired leaves no trace.** The fix is not vigilance, it is a
   field: a per-config record should carry the SET of gates that produced its verdict, so
   "oracle-only" is visibly different from "oracle + sanitizer". Then a missing gate shows up as
   data rather than as absence.
2. **An output oracle is weakest where the computation is most forgiving.** Reductions, clamps,
   argmin/argmax and anything idempotent can absorb a wrong element without changing the output.
   Those are precisely the kernels that need an orthogonal check.
3. **The lapse was found by remediating a *known* process failure, not by suspecting these three
   kernels.** The gate lapse was already on the deviations register as a documentation problem.
   Running the bounded remediation turned it into a measurement finding that changed three classes
   and invalidated a 13× result. Process deviations are worth re-testing empirically, not just
   disclosing.
