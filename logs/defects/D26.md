# D26 — a scaffolded driver made the correctness oracle unfalsifiable, and cytune certified an improvement on a flat kernel

**Step:** launch pass, section D1 (beginner tester agent). **Date:** 2026-08-12.
**Status:** fixed, validated (live repro refuses; live negative control still runs).
**Found by:** a **first-time-user agent**, on the **first kernel it wrote**, with no prompting to
look for this. It was asked to use the three-command path as a beginner would.
**Raw:** `src/cytune/init.py` `_SCALARS`, `src/cytune/session.py::Session.oracle_power`.
Recompute: `.venv/bin/python -m pytest src/cytune/test_cytune_oracle_power.py`.

## Summary

The tester wrote `clip(double[::1] x, double lo, double hi)`. `cytune init` scaffolded **`lo = 1.0`
and `hi = 1.0`** — every float-ish scalar got the same literal. With `lo == hi`, the kernel returns
a constant array. Same kernel, same machine, same flags, one line of the driver different:

| driver | verdict | exit |
|---|---|---|
| exactly as `cytune init` wrote it | **IMPROVEMENT, 1.0790x** | 0 |
| `lo=-2.0, hi=2.0` | HONEST-FLAT, 1.0000x | 2 |

`init` reported `DRIVER CONTRACT: passes`. `doctor` reported READY. The certificate reported
`rejected as incorrect: 0 (0.0% of measured)`. The sanitizer gate was CLEAN. **`--apply` accepted
it** and wrote `# cython: boundscheck=False, wraparound=False, …` into the user's source — the exact
header the README warns can turn a latent off-by-one into an out-of-bounds read.

Nothing in the run hinted that anything was wrong.

## Root cause — two of them, at different depths

**The proximate cause** is one line of `init.py`: `_SCALARS` maps `double -> "1.0"`, so *n* scalars
of the same type all scaffold the same value. Two invented values that happen to be equal is not an
exotic corner; it is the default outcome for any kernel taking a low and a high.

**The real cause is that G1 had no positive control.** The guarantee "it will not recommend a
configuration that produces wrong output" is implemented as: compare each build's canonical output
against a golden. If the golden is a constant array, **that comparison cannot fail**. Every build
matches. The certificate's `rejected as incorrect: 0 (0.0%)` is then not evidence, it is
arithmetic — and it is displayed in the position where evidence goes.

This project requires a positive and a negative control of every instrument it builds: a planted 2×
lever must be detected, a known-flat kernel must read flat, the fleet gate must fail on
reintroduced D-2. The **oracle** — the instrument the whole correctness guarantee is made of — had
neither.

## Why nothing caught it

- `init`'s driver-contract check verifies the four names exist and the driver *runs*. It cannot
  know that the values it invented were degenerate.
- The determinism gate asks "same input ⇒ same output". A constant output passes it perfectly.
- The oracle asks "does this build match the golden". A constant golden makes that vacuous.
- 910 tests and a live smoke gate all exercise kernels whose outputs vary, so none of them was in a
  position to notice.

Every check present asked a question the degenerate case answers correctly.

## Fix

**1. The consequence — `Session.oracle_power()` (`session.py`), called from `Session.golden()`.**
After the golden is captured, load it and ask whether the oracle *can* fail: a multi-element output
whose every element is identical means it cannot. `cli.tune` then **refuses**, exit 1, and names
the likely cause:

```
cytune: REFUSING TO TUNE — the correctness oracle has no power on this workload.
  Your driver's canon() returned 238708 values and every one of them is identical.
  Nothing cytune measures could ever fail that check, so G1 ... would be vacuous
```

Two judgements inside it, both deliberate:

* **A single-valued output is NOT degenerate.** A reduction legitimately returns one number, and
  refusing those would refuse a whole class of real kernels. What is degenerate is a *multi-element*
  output that is constant.
* **`checked: False` is never read as `degenerate: False`.** An unreadable or missing golden is
  reported as not-checked, following the same rule as the sanitizer gate: a control that could not
  run is not a control that passed.

It reads the `golden.npy` the vendored rig already wrote and does **not** modify
`_vendor/campaign.py`, which is hash-pinned to the study source and may not diverge from it. A test
asserts that, on the AST rather than on the text.

**2. The cause — `init._make_input_expr(..., scalar_ordinal=n)`.** Repeated scalars of the same
type now get distinct values. The *first* scalar keeps the value `USER_GUIDE` §0 documents, so a
single-scalar kernel scaffolds exactly what the guide says; only repeats are perturbed.

Both, because a user can write a degenerate driver by hand, and `init` can invent a collision on a
kernel whose oracle would be fine otherwise.

## What this says about the tester campaign

D26 was found in **fourteen minutes** by an agent told to behave like a beginner, on the first
kernel it invented. No test, no gate, no audit, and no amount of reading the code had found it in
the project's history.

The reason is structural and worth stating: every existing check was written by someone who knew
what the tool was for, and therefore wrote drivers that exercised it properly. The degenerate case
is not something you reach by trying to break the tool — it is something you reach by **using it
normally on a kernel with two bounds**.

The same agent also found that `--help` and every certificate cited `results/PHASEP_REPORT.md §5`,
a path tracked on **no branch** (`git ls-files results/` returns zero). Fixed, and now guarded by
`test_no_user_facing_string_points_at_a_path_the_user_does_not_have`, which scans string literals
and deliberately exempts docstrings — a maintainer reading the source is on a branch that has it.

## Class

**"The instrument has no control on itself."** D23 is its sibling: the sanitizer gate never ran, so
1,296 out-of-bounds configurations were recorded feasible on the oracle alone. Both are cases where
the *checking* machinery was in place and nothing verified the checking machinery could produce a
negative.

The class defence is narrow but real: G1's control now runs on every single tune. There is no
equivalent standing control for the *tolerance* the oracle uses, and none is claimed.
