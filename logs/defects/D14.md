# D14 — certificate said "fast-math: not opted in" while emitting `-ffp-contract=fast` (undisclosed FP-semantics change)

**Step:** P4-alpha CLI v0 (Amendment A-4), E2E smoke run 1. **Date:** 2026-07-25.
**Status:** fixed, validated (commit `7caa145`; composition check green on current code and RED on
a disclosure-stripped certificate). **Raw:**
`results/cli_v0/ws/toy_running_max/certificate.{json,txt}`. Recompute:
`python3 scripts/cytune_e2e_composition_check.py`.

## Summary

The emitted GCC flags contained `-ffp-contract=fast`, which permits the compiler to fuse
multiply-add pairs and therefore changes floating-point results — while the same certificate
stated `FAST-MATH: not opted in`. Both statements were individually true; together they invited a
user who had declined fast-math to conclude that floating-point semantics were untouched. Fixed by
adding a `FLOATING-POINT SEMANTICS` disclosure block covering every value-affecting flag actually
emitted.

## Symptom

Smoke run 1 (`toy_running_max`) certificate:

```
GCC flags:
  -O3 -march=native -fno-unroll-loops -ffp-contract=fast
...
FAST-MATH: not opted in (--allow-fast-math). Fast-math configs were excluded from selection.
```

## Root cause

The search space's composite `fmffp` factor (`scripts/phasep/theta.py`, PREREG §0.1) has **three**
levels: `("off","off")`, `("off","fast")`, `("on","NA")`. Only `("on","NA")` is `-ffast-math`.
The middle level leaves fast-math off but sets `-ffp-contract=fast`, permitting FMA contraction.

`src/cytune/certify.py::build_certificate` computed exactly one predicate:

```python
uses_fm = bool(cfg and cfg[8][0] == "on")
```

and the rendered `FAST-MATH:` line was driven by that single bit. The `("off","fast")` level had no
representation anywhere in the certificate, so a config from that level was reported under the same
"not opted in" banner as a fully strict config.

The study's own vocabulary made this easy to miss: `delta_strict` is defined over
`config[8][0] == "off"`, which *includes* `("off","fast")`. "Strict" in the study means "not
fast-math", not "bit-identical FP semantics" — and the certificate inherited the study's binary
without inheriting the caveat.

## Why it produced the symptom

`-ffp-contract` is one of the few flags whose GCC default is `fast`. The project already requires it
to be explicit for exactly this reason (CLAUDE.md: "`-ffp-contract` always explicit"). Because the
flag was correctly emitted and correctly measured, and because the oracle passed at the derived
tolerance, every mechanical check was satisfied. The failure was purely one of disclosure: the
certificate is the product, and it described the run in a way that understated what had changed.

## Fix

`src/cytune/certify.py`: added `uses_contract` (true when `cfg[8] == ("off","fast")`) and an
`fp_semantics` certificate field rendered as a `FLOATING-POINT SEMANTICS` block. It states what
contraction does, that it is **not** `-ffast-math` (no reassociation, no finite-math assumptions),
and that it was accepted only because it passed the oracle at the stated tolerance. When
contraction is off, the field records that `-ffp-contract` is explicit precisely because GCC's
default would otherwise permit it silently.

The fix addresses the root cause — a two-valued report of a three-valued factor — rather than
softening the `FAST-MATH:` wording.

## How it was found

Reading smoke run 1's certificate against the emitted flag list, immediately after the run
succeeded. Nothing failed; the output simply did not survive being read carefully.

## Why it slipped through

**Review miss at a vocabulary seam.** The certificate code was written against the study's
strict/fast-math binary, which is correct *for the study's questions* (Δ_strict) and incomplete for
a product's disclosure duty. No test asserted "every value-affecting flag emitted is disclosed",
because the property is about the relationship between two independently-correct outputs.
