# D12 — /home filled to 100% mid wave-2 (unpruned _so build caches); one ENOSPC-overlapped build discarded

**Step:** P-2 wave-2 top-up (Amendment A-3), ~6 acceptances in. **Date:** 2026-07-24.
**Status:** fixed, validated (disk 45%, rig verify PASS, runner resumed, 0 measurement data lost).
**Raw:** `df -h /home` → `43G 42G 0 100%` at failure; `du -sh results/fleet` → 52G.

## Symptom

A routine `git add`/`commit` of an accepted wave-2 kernel failed with
`fatal: … index.lock write error. Out of diskspace`. `df` showed `/home` at **100%, 0 avail**.
The fleet directory had grown to **52 GB** on a 43 GB partition.

## Root cause

Each measured kernel keeps a `_so/` directory (1,728 compiled `.so`, one per config) plus a
`_ccache/` cythonize cache — **~355 MB per kernel**. These are build artifacts, gitignored
(`results/fleet/**/_so/`, `**/_ccache/`), and were **never pruned**. Across ~130 wave-1 + wave-2
kernel directories that is ~46 GB of reproducible build cache — it crossed the partition ceiling
partway through wave-2. Not a code defect in the runner; a capacity-management gap: nothing in the
pipeline reclaims a kernel's build cache once its table + class are committed.

## The correctness risk (why a kernel was discarded, not kept)

At the moment the disk filled, the current slot `FLAT_FM_W2_52 fm_sumsq` was in its **build phase**
(no `table.jsonl` yet). `build_phase.py` caches a failed compile as **feasibility-0** ("cythonize-
fail ⇒ whole-combo feasibility-0 cached once", inherited CF rule). An **ENOSPC** write failure is
transient and environmental, not a real cythonize failure — but the cache cannot tell them apart,
so any config that failed to write its `.so` during the full-disk window would be **spuriously
cached infeasible**, corrupting fm_sumsq's `infeasible_frac`, its FEAS flag, and possibly its
class. Correctness is absolute and this kernel would enter the frozen decision-grade dataset, so
the build was **discarded and rebuilt fresh**, not inspected-and-maybe-kept.

## Fix

1. **Reclaim (safe):** deleted `_so/` + `_ccache/` for all **262** completed kernel subdirs
   (those with a committed `class_v2.json`), sparing the in-flight kernel. Safe because the build
   is deterministic and reproducible from the committed `kernel.pyx`/`driver.py`, the measurement
   data (`table.jsonl`, `class_v2.json`, `endpoint.json`) is committed to git, and every
   downstream consumer — the freeze manifest (hashes `table.jsonl`/`class_v2.json`), the sealed
   study (reads frozen `table.jsonl`), and both auditors (recompute from raw `table.jsonl`) — reads
   those, never `_so`. Freed **23 GB** (100% → 45%).
2. **Discard the contaminated build:** killed the runner + build container, removed the
   `fm_sumsq` kernel dir (build products only, no measurement existed), verified the rig quiesced
   (`measure_wrap --verify-only` PASS), relaunched `--stage topup` — which resumed at `fm_sumsq`
   and rebuilt it on a healthy disk. The 6 prior acceptances were untouched and intact.
3. **Prevent recurrence:** prune completed-kernel `_so`/`_ccache` at **every steward tick** for the
   remainder of P-2 (wave-2 top-up, H, R), keeping `/home` bounded. Not wired into the runner —
   editing the operative runner mid-campaign is a needless risk; the steward loop owns it.

## Cap accounting (honest)

The ~25 min of CPU spent on the discarded `fm_sumsq` build is **operational cost of an
environment fault**, not valid top-up measurement, and is **not charged to the A-3d cap** (the
in-flight marker was cleared on discard). This mirrors how runner-death idle time is treated
(operational, outside the measurement envelope; STATE `P2_envelope_actuals`). It is recorded here
so the envelope accounting in the P-2 report is complete rather than silently favorable.

## Validation

`df -h /home` → 45% used, 23 G avail. `measure_wrap --verify-only` → PASS (rig quiesced). Runner
relaunched, in-flight = `fleet_FLAT_FM_W2_52_fm_sumsq` (fresh rebuild). Ledger: 6 wave-2
acceptances intact, all committed. **Zero measurement data lost** — every discarded byte was a
reproducible build artifact or an unmeasured, ENOSPC-suspect build.

## Lesson

Reproducible build caches are not free just because they are gitignored — they are real bytes on a
finite disk, and on a long unattended campaign they accumulate past the ceiling. Any pipeline that
writes a large per-unit cache needs an explicit reclaim step tied to "this unit is durably
recorded" (here: table + class committed). And a full disk is a **correctness** event, not merely
an availability one: a build/measure that overlaps ENOSPC must be treated as suspect and
discarded, because the failure can masquerade as real infeasibility in exactly the cache the
taxonomy depends on. Distinguish operational compute (discarded, environment-caused) from
measurement compute (charged) in the budget, and say which is which.
